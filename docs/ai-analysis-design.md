# Arbalest: Slack の会話を AI で分析する方式（設計メモ）

対象: スレッド・チャネルの会話から、決定事項・未決定事項・ToDo・Findings を取り出す処理。
AI の提供元は Azure AI Foundry（OpenAI 互換）を最初に使うが、提供元に依存しない作りにする。

## 基本の考え方

1. **AI には事実の抽出だけをさせ、判定・整形・リンク生成はコードで行う。** AI の出力は JSON のみ。
2. **すべての項目に根拠のメッセージ ID を付けさせ、コードで検証する。** 根拠のない項目は落とすか「要確認」にする。
3. **前処理でトークンを減らし、曖昧さ（人名・日付）をコードで解決してから渡す。**
4. **差分で更新する。** 2回目以降は、前回の状態と新しいメッセージだけを渡す。
5. **評価用のデータセットで比較してから、プロンプトやモデルを変える。**

## 処理の流れ

```
取得 → 前処理(コード) → 量で分岐 ─┬→ 1回で抽出（大半のスレッド）
                                 └→ 分割して抽出 → 統合（長いチャネル・Findings）
     → 検証(コード) → 状態の判定(コード) → 差分の保存(Firestore) → 表示の生成(コード)
```

## 1. 前処理（コード、AI を使わない）

- **不要なメッセージを除く**: join/leave、チャネル名の変更などの subtype、ボット自身の投稿。
- **編集されたメッセージ**: 最新の本文だけを使う。
- **Slack の記法を読める形に直す**: `<@U123>` → `@田中`、`<url|ラベル>` → `ラベル`、`<#C123>` → `#チャネル名`。ユーザー名は `users.info` の結果をキャッシュする。
- **1行の簡潔な形式にする**（JSON より大幅に少ないトークンで済む）:
  ```
  [m12] 10/23(金) 14:03 田中 → m10: 来週火曜の午後でどうですか  {👍×3: 佐藤,鈴木,高橋}
  ```
  - `m12` は短い連番の ID。Slack の `ts` との対応はコードで持ち、パーマリンクはコードで作る（AI に URL を書かせない）。
  - リアクションは**合意のシグナル**として、誰が付けたかまで含める。日程調整では「👍 だけで合意した」ことが多いため。
  - 返信先（スレッドの親、引用）を `→ m10` で示す。
  - 添付ファイルは名前だけにする。
- **日付の手がかりを渡す**: 各メッセージに JST の日時と曜日を付ける。プロンプトには「今日の日付」と「今日から前後3週間の日付と曜日の表」を入れる。「来週火曜」のような相対表現を AI が誤らないようにするため。
- **参加者の一覧を渡す**: `U123=田中` の対応表を作る。担当者の欄は、スキーマの enum でこの ID に限定する。存在しない人へのリマインドを防ぐため。
- **トークン数を数え**（`gpt-tokenizer` など）、1回で処理するか分割するかを決める。

## 2. 抽出（AI）

### 事実を細かく取り出し、決定かどうかはコードで判定する

日程調整は「候補 → 各人の回答 → 確定」という状態の変化として扱える。
AI には次の**細かい事実**を出させ、「決定」「未決定」の判定はコードの規則で行う。

| 抽出する事実 | 例 |
|---|---|
| `proposal`（提案された候補） | 「10/28(火) 午後」 |
| `response`（候補への各人の回答） | 佐藤: 可 / 鈴木: 不可 / 高橋: 不明 |
| `decision_statement`（明示的な確定の発言） | 「では 10/28 15時で確定します」 |
| `todo` | 「会議室を予約する（担当: 田中、期限: 10/27）」 |
| `open_question`（未解決の問い） | 「場所はオンラインか対面か」 |

コードでの判定の例: 「明示的な確定の発言がある」または「必要な参加者が全員『可』と回答した」場合だけを決定とする。それ以外は未決定とし、誰の回答が残っているかを示す。
AI に「決定かどうか」を直接判断させるより、ぶれと誤りが減る。判定の規則もテストで固定できる。

### スキーマの工夫

- **根拠を先に書かせる**: 各項目は `evidence`（メッセージ ID の配列）と `quote`（根拠の短い引用）を先に置き、結論の欄をその後に置く。モデルが根拠から結論を書く順になる。
- **曖昧さを表す欄を用意する**: `certainty: "explicit" | "implied" | "uncertain"`。敬語の曖昧な表現（「問題ないかと思います」）をどう扱うかを、プロンプトで具体例とともに定める。
- **日付の書き方**: `due` は ISO 形式の日付と、元の表現（`due_text: "来週火曜"`）の両方を出させる。
- **構造化出力**（`response_format: json_schema, strict: true`）を使い、zod で検証する。失敗したら1回だけ再試行する。

### プロンプトの構成（プロンプトキャッシュを効かせる）

Azure OpenAI は、先頭が同じプロンプトの部分を自動でキャッシュする（1024 トークン以上の場合）。そのため、変わらない部分を前に、変わる部分を後ろに置く。

```
[system] 役割、抽出の規則、判定の例（few-shot）、注意事項   ← 毎回同じ（キャッシュされる）
[user]   今日の日付・日付の表、参加者の一覧、前回の状態、メッセージ  ← 毎回変わる
```

## 3. 長い会話（Findings、長いチャネル）: 分割して抽出し、統合する

- **分割の単位**: スレッドの途中では切らない。「スレッド単位」または「日・週単位」でまとめ、トークンの上限に収める。
- **抽出（map）**: 安いモデルで、分割ごとに Findings の候補を根拠の ID 付きで取り出す。
- **統合（reduce）**: 強いモデルで、重複をまとめ、矛盾を指摘し、テーマごとに整理する。
- **抽出結果を保存する**: キーは「チャネル、期間、本文のハッシュ、プロンプトの版」。期間が重なる Findings を再実行するとき、同じ部分は AI を呼ばずに済む。
- 無償プランでは、取得できる履歴は直近90日まで。

## 4. 差分の更新（スレッドのまとめを繰り返し呼ぶ場合）

- Firestore に、スレッドごとの**状態**（抽出した事実と項目の ID）と、最後に処理したメッセージの `ts` を保存する。
- 2回目以降は「前回の状態と、その後のメッセージ」だけを渡す。AI には**変更の操作**（`add` / `update` / `close`、項目の ID 付き）を出させる。
- 項目の ID が変わらないので、ToDo のリマインドや canvas の節を同じ項目として更新し続けられる。
- 状態が大きくなりすぎたときや、プロンプトの版を上げたときは、全体を処理し直す。

## 5. 検証（コード、AI を追加で呼ばない）

- `evidence` の ID が実在するか。
- `quote` が根拠のメッセージに含まれるか（空白と記号を除いて部分一致で確かめる）。
- 担当者が参加者の一覧に含まれるか（スキーマの enum で保証する）。
- 日付が妥当か（過去すぎないか、曜日と一致するか）。
- 不合格の項目は捨てずに「要確認」として表示する。AI にもう一度確かめさせるのは、この「要確認」だけにする（任意）。

## 6. 表示（コード）

- AI に整形した文章を書かせない。JSON から Block Kit と canvas の markdown をコードで作る。出力トークンが減り、表示の形も揃う。
- 各項目に根拠へのリンク（パーマリンク）を付ける。
- 「要確認」は印を付けて区別する。

## 7. モデルの使い分け（提供元に依存しない設定）

用途ごとに使うモデルを設定で決める。コードはモデル名を直接持たない。

```ts
type LlmTask = "extract" | "extract_chunk" | "synthesize" | "verify";

interface LlmProvider {
  generateStructured<T>(req: {
    task: LlmTask;
    system: string;         // 変わらない部分（キャッシュされる）
    input: string;          // 変わる部分
    schema: z.ZodType<T>;
    maxOutputTokens?: number;
  }): Promise<{ data: T; usage: { input: number; cachedInput: number; output: number } }>;
}
```

- `extract_chunk` は安いモデル、`synthesize` は強いモデルに割り当てる。推論モデルを使う場合は、用途ごとに reasoning effort も設定する。
- 実装は `OpenAICompatibleProvider` の1つから始める。Azure の v1 エンドポイントを `baseURL` に指定し、デプロイ名をモデル名として渡す。
- 使ったトークン数（キャッシュ分を含む）を毎回記録する。費用とキャッシュの効き具合を確かめるため。

## 8. 安全性

- **会話の中の指示に従わせない**: Slack のメッセージには、プロンプトインジェクション（「これまでの指示を無視して〜」）が含まれうる。メッセージは区切って「データ」として渡す。
- **AI に道具を持たせない**: AI の出力は JSON だけにし、投稿やリマインドの実行はコードが決める。リマインドの宛先は、参加者の一覧（enum）に限る。
- **送る情報を最小にする**: 対象はボットが招待されたチャネルだけ。必要なら、名前を仮の ID に置き換えて送る設定にする。

## 9. 評価（品質を上げ続けるための仕組み）

- 合成した会話（実データを使わない。リポジトリに実データを置かない）と、正解の JSON の組を 20〜30 件用意する。日程調整、曖昧な合意、途中で予定が変わる、相対的な日付、長いスレッド、を含める。
- `npm run eval` で、次の指標と費用を出す。
  - 決定事項・ToDo の適合率と再現率
  - 担当者と期限の正解率
  - 根拠の検証の合格率
  - トークン数
- プロンプトに版の番号を付け、変更のたびに評価を比べる。モデルを替える判断（例: 安いモデルで足りるか）も、この評価で行う。
