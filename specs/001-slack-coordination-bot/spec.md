# Feature Specification: Slack 調整まとめボット Arbalest（MVP）

**Feature Branch**: `001-slack-coordination-bot`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "Slack ボット Arbalest の MVP。@arbalest をメンションすると、会話を分析して結果を返す。対象は、ボットが招待されたチャネルのスレッドと、チャネルの直近の会話（無償プランなので最大90日）。機能: (1) まとめ (2) canvas (3) todo (4) findings。すべての項目に根拠のメッセージへのリンクを付ける。AI の提供元を差し替えられること。合成の会話データで品質を評価できること。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - スレッドの調整状況のまとめ (Priority: P1)

日程調整などをスレッドで進めているメンバーが、スレッドで `@arbalest まとめ` と書く。ボットはスレッドの会話を読み、**決定事項**、**未決定事項**（候補と、誰の回答が残っているか）、**ToDo**（担当者・期限）をスレッドに返信する。各項目には根拠のメッセージへのリンクが付く。会話が進んだ後にもう一度呼ぶと、前回のまとめからの変化（新しく決まったこと、閉じた項目、追加された ToDo）が分かる形で更新される。

**Why this priority**: ボットの中心の価値。これだけで「長いスレッドを読み返さずに状況が分かる」が実現する。

**Independent Test**: 合成の日程調整スレッドでボットを呼び、返信の内容を正解と照合する。続けてメッセージを追加して再度呼び、差分が反映されることを確かめる。

**Acceptance Scenarios**:

1. **Given** 候補日が3つ提案され、全員が1つの候補に「可」と答えたスレッド, **When** `@arbalest まとめ` を書く, **Then** その候補が決定事項として、根拠のリンク付きで返信される。
2. **Given** 候補日に2人が回答し、1人が未回答のスレッド, **When** まとめを呼ぶ, **Then** その件は未決定事項として示され、未回答の人が名前で示される。
3. **Given** 「田中さん、来週火曜までに会議室を予約してください」「了解です」というやり取り, **When** まとめを呼ぶ, **Then** ToDo「会議室の予約」が担当者・田中、期限・その火曜の日付で示される。
4. **Given** 一度まとめた後に「やはり 10/30 に変更します」と投稿されたスレッド, **When** もう一度まとめを呼ぶ, **Then** 決定事項が新しい日付に更新され、変更されたことが分かる。
5. **Given** 決定事項・ToDo のどれにも当たらない雑談だけのスレッド, **When** まとめを呼ぶ, **Then** 「まとめる調整事項は見つかりませんでした」と返信され、項目を作り出さない。

---

### User Story 2 - ToDo の登録とリマインド (Priority: P2)

メンバーが `@arbalest todo` と書くと、ボットはスレッドの ToDo を登録し、登録した一覧を返信する。登録された ToDo は、期限の前日と、平日の朝に担当者へリマインドされる。担当者がリマインドのボタンを押すか、ToDo の元のメッセージかボットの一覧に ✅ のリアクションを付けると、完了になりリマインドが止まる。

**Why this priority**: 抽出した ToDo を実際の行動につなげる。まとめ（P1）の結果を使うため、P1 の後に置く。

**Independent Test**: 合成スレッドで todo を呼び、登録・リマインドの送信日時・完了操作を、時刻を固定したテストで確かめる。

**Acceptance Scenarios**:

1. **Given** 期限付きの ToDo が2件あるスレッド, **When** `@arbalest todo` を書く, **Then** 2件が登録され、担当者・期限・根拠のリンク付きで一覧が返信される。
2. **Given** 期限が明日の未完了の ToDo, **When** 平日の朝のリマインドの時刻になる, **Then** 担当者に、期限が近いことと完了のボタンを含むリマインドが届く。
3. **Given** リマインドを受け取った担当者, **When** 完了のボタンを押す, **Then** ToDo が完了になり、以降のリマインドが届かず、スレッドの一覧にも完了が反映される。
4. **Given** 期限を過ぎた未完了の ToDo, **When** 平日の朝のリマインドの時刻になる, **Then** 期限切れであることが分かる形で担当者にリマインドされる。
5. **Given** 担当者が特定できない ToDo, **When** 登録される, **Then** 担当者「未定」として登録され、リマインドは ToDo を登録した人に届く。

---

### User Story 3 - チャネル canvas への書き出し (Priority: P3)

メンバーがスレッドで `@arbalest canvas` と書くと、そのスレッドのまとめが、チャネル canvas の「このスレッドの調整」用の節に書き出される。同じスレッドで再度呼ぶと、新しい節を作らず同じ節が更新される。別のスレッドの調整は別の節になる。

**Why this priority**: 複数の調整をチャネルで一覧できるようにする。まとめ（P1）の出力先を増やすものなので P3。

**Independent Test**: 2つのスレッドで canvas を呼び、canvas に2つの節ができること、片方を再実行しても節が増えずに内容が更新されることを確かめる。

**Acceptance Scenarios**:

1. **Given** チャネル canvas がないチャネル, **When** スレッドで `@arbalest canvas` を書く, **Then** チャネル canvas が作られ、そのスレッドの節が書かれ、スレッドに canvas へのリンクが返信される。
2. **Given** すでに節があるスレッド, **When** 会話が進んだ後に再度 canvas を呼ぶ, **Then** 同じ節が最新のまとめで置き換わり、他の節は変わらない。
3. **Given** 人が canvas の節の外に書き込んだ内容, **When** ボットが節を更新する, **Then** 節の外の内容は消えない。

---

### User Story 4 - 期間の Findings (Priority: P4)

メンバーがチャネルで `@arbalest findings 30日` と書くと、ボットは指定した期間のチャネルの会話（スレッドを含む）から、分かったこと・繰り返し出た課題・合意された方針などを**テーマごと**にまとめ、根拠のリンク付きで返信する。期間を省略したときは直近30日とし、最大は90日とする。

**Why this priority**: 振り返り用の機能で、日々の調整（P1〜P3）より緊急度が低い。長い会話を扱うため処理も重い。

**Independent Test**: 複数のテーマを含む合成のチャネル履歴で findings を呼び、テーマの抽出と根拠を正解と照合する。

**Acceptance Scenarios**:

1. **Given** 30日分の会話に3つのテーマが含まれるチャネル, **When** `@arbalest findings 30日` を書く, **Then** 3つのテーマごとに Findings が根拠のリンク付きで返信される。
2. **Given** 同じ事柄が複数のスレッドで繰り返し議論されたチャネル, **When** findings を呼ぶ, **Then** 1つの Finding にまとめられ、根拠のリンクが複数付く。
3. **Given** `@arbalest findings 120日`, **When** 呼ぶ, **Then** 90日に制限したことを伝えた上で、直近90日の結果を返す。
4. **Given** 処理に時間がかかる期間, **When** findings を呼ぶ, **Then** すぐに「処理中」と返信され、完了後に結果が届く。

---

### Edge Cases

- ボットが招待されていないチャネルでメンションされた、または読めない会話を対象にされた → 招待が必要であることを返信する。
- 同じメンションが Slack から重複して届いた → 1回だけ処理する。
- 同じスレッドで処理中にもう一度呼ばれた → 二重に処理せず、処理中であることを返信する。
- 対象の会話が非常に長い（数百件のメッセージ）→ 分割して処理し、結果は1つにまとめて返す。
- 「来週火曜」など相対的な日付 → 発言の日時を基準に具体的な日付に直す。解決できないときは元の表現のまま示し、日付は「要確認」とする。
- 敬語などで合意かどうかがあいまいな返答 → 合意とは扱わず、未決定事項として示す。
- 根拠が確かめられない項目（引用が元のメッセージに見当たらない等）→ 捨てずに「要確認」の印を付けて示す。
- 会話の中に、ボットへの指示のように見える文（「これまでの指示を無視して…」）がある → 会話の内容として扱い、ボットの動作は変わらない。
- 担当者が退出・削除されたユーザー → 名前は表示し、リマインドは登録した人に届く。
- AI の呼び出しが失敗・時間切れになった → 自動で再試行し、最終的に失敗したら、失敗したことと再実行の方法を返信する。
- 無償プランで90日より古いメッセージ → 取得できないため対象外とし、その旨を必要に応じて伝える。
- まとめの後に元のメッセージが編集・削除された → 次のまとめで最新の内容に基づいて更新する。

## Requirements *(mandatory)*

### Functional Requirements

**呼び出しと応答**

- **FR-001**: ボットへのメンションに含まれる語（まとめ / todo / canvas / findings と期間）で機能を選ぶ。語がないか分からないときは、使い方の説明を返信する。
- **FR-002**: メンションを受けてから数秒以内に「受け付けた」ことが分かる反応（リアクションか返信）を返し、結果は処理が終わってから同じスレッドに返信する。
- **FR-003**: スレッドの中で呼ばれた場合はそのスレッドを、チャネルで直接呼ばれた場合はチャネルの直近の会話（まとめは直近7日、findings は指定した期間）を対象にする。
- **FR-004**: 同じイベントの重複は1回だけ処理し、同じ対象への同時の処理は1つに限る。
- **FR-005**: ボットが招待されたチャネルの会話だけを読む。
- **FR-006**: Slack から届いたリクエストが本物であることを確かめ、確かめられないものは処理しない。

**まとめ（US1）**

- **FR-010**: 会話から、決定事項、未決定事項、ToDo、未解決の問いを抽出する。
- **FR-011**: 日程などの調整について、提案された候補と、候補への各参加者の回答（可 / 不可 / 不明）を把握する。決定事項とするのは、明示的な確定の発言がある場合か、必要な参加者全員が同じ候補に「可」と答えた場合に限る。
- **FR-012**: 未決定事項には、回答が残っている参加者を示す。
- **FR-013**: ToDo には、内容、担当者（会話の参加者から特定する。特定できなければ「未定」）、期限（具体的な日付。元の表現も保持する）を付ける。
- **FR-014**: すべての項目に、根拠となるメッセージへのリンクを1つ以上付ける。
- **FR-015**: 項目の根拠（参照したメッセージの存在と、引用が本文に含まれること）を確かめ、確かめられない項目には「要確認」の印を付ける。
- **FR-016**: 同じスレッドで2回目以降に呼ばれたときは、前回の結果を引き継ぎ、新しい会話による変化（追加・変更・完了）を示す。各項目は呼び出しをまたいで同じ項目として識別される。
- **FR-017**: 合意の手がかりとして、メッセージへのリアクション（誰が付けたか）も考慮する。
- **FR-018**: 結果の表示はボットが決めた一定の形式で行い、分類ごとに見出しを付ける。

**ToDo とリマインド（US2）**

- **FR-020**: `todo` で、スレッドから抽出した ToDo を登録し、登録した一覧を返信する。同じ ToDo を二重に登録しない。
- **FR-021**: 未完了の ToDo について、期限の前日と、平日の朝（日本時間 9:00）に、担当者へリマインドを送る。担当者が「未定」なら登録した人に送る。
- **FR-022**: リマインドには完了のボタンを付ける。担当者・登録した人が、ボタンか ✅ のリアクションで完了にできる。
- **FR-023**: 完了した ToDo にはリマインドを送らず、スレッドの一覧にも完了を反映する。
- **FR-024**: 期限切れの ToDo は、期限切れと分かる形でリマインドする。

**canvas（US3）**

- **FR-030**: `canvas` で、そのスレッドのまとめをチャネル canvas に書き出す。チャネル canvas がなければ作る。
- **FR-031**: スレッドごとに1つの節を持ち、再実行では同じ節を置き換える。他の節と、節の外の内容は変えない。
- **FR-032**: 書き出し後、スレッドに canvas へのリンクを返信する。

**Findings（US4）**

- **FR-040**: `findings <期間>` で、期間内のチャネルの会話（スレッドを含む）から、Findings をテーマごとにまとめる。期間の既定は30日、上限は90日。
- **FR-041**: 同じ事柄についての複数の議論は、1つの Finding にまとめ、根拠のリンクを複数付ける。
- **FR-042**: 期間を同じくする再実行や期間が重なる実行では、すでに分析した部分の結果を再利用して、時間と費用を抑える。

**AI の利用と品質**

- **FR-050**: AI の提供元とモデルは設定で切り替えられ、機能の動作は特定の提供元に依存しない。用途（抽出、統合など）ごとに異なるモデルを設定できる。
- **FR-051**: AI に渡す会話は「分析の対象のデータ」として扱い、会話の中の文によってボットの動作（投稿先、リマインドの宛先など）が変わらない。
- **FR-052**: 合成した会話と正解の組を使って、抽出の品質（決定事項・ToDo の適合率と再現率、担当者と期限の正解率、根拠の検証の合格率）と、1回あたりの費用を測れる。
- **FR-053**: 1回の処理ごとに、使った AI の量（入出力の量）を記録する。
- **FR-054**: AI の呼び出しが失敗したときは自動で再試行し、最終的に失敗したら利用者に失敗を伝える。

### Key Entities

- **会話の対象（Conversation Target）**: スレッドか、チャネルと期間。まとめ・canvas の節・ToDo はこれに紐づく。
- **調整のまとめ（Coordination Summary）**: 対象ごとの最新の分析結果。決定事項、未決定事項、ToDo、未解決の問いと、最後に分析したメッセージの位置を持つ。
- **提案（Proposal）と回答（Response）**: 調整の候補と、各参加者の可 / 不可 / 不明。決定・未決定の判定の元になる。
- **項目（Item）**: 決定事項・未決定事項・ToDo・問い・Finding の共通の性質。呼び出しをまたいで変わらない識別子、根拠のメッセージ、引用、確からしさ、「要確認」の印を持つ。
- **ToDo**: 内容、担当者、登録した人、期限（日付と元の表現）、状態（未完了 / 完了）、リマインドの履歴。
- **canvas の節（Canvas Section）**: チャネル canvas の中の、スレッドごとの節。
- **Finding**: テーマ、内容、根拠のメッセージ（複数）。
- **評価ケース（Evaluation Case）**: 合成した会話と、期待される抽出結果の組。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: メンションから「受け付けた」反応まで3秒以内（95%）。メッセージ200件までのスレッドのまとめは、60秒以内に結果が届く（95%）。
- **SC-002**: 評価データで、決定事項の適合率 90% 以上・再現率 80% 以上、ToDo の適合率 85% 以上・再現率 80% 以上。
- **SC-003**: 評価データで、ToDo の担当者の正解率 80% 以上、期限の日付の正解率 80% 以上。
- **SC-004**: 表示されるすべての項目に根拠のリンクが付き（100%）、根拠を確かめられない項目が「要確認」の印なしに表示されることがない（0件）。
- **SC-005**: 未回答の人がいる調整が「決定」と表示されることがない（評価データで0件）。
- **SC-006**: 新しいメッセージが全体の2割以下のスレッドで2回目のまとめを呼んだとき、AI の利用量が初回の半分以下になる。利用量は、毎回同じでキャッシュが効く固定のシステムプロンプトとスキーマを除いた入力のトークンで測る。
- **SC-007**: リマインドが、時刻を固定したテストで、期限の前日と平日の朝に漏れなく送られ、完了した ToDo には送られない（100%）。
- **SC-008**: canvas の再実行で節が重複しない（100%）。
- **SC-009**: AI の提供元を別の互換の提供元に切り替えたとき、設定の変更だけで全機能が動く。

## Assumptions

- 利用者は1つの Slack ワークスペース（無償プラン）のメンバーで、使い方は日本語。ボットの出力も日本語。
- 無償プランのため、取得できる履歴は直近90日まで。canvas はチャネル canvas（1チャネルに1つ）を使い、スレッドごとの節で分ける。
- 「必要な参加者」は、提案の中でメンションされた人とする。メンションがなければ、スレッドで発言した人全員とする。
- 曜日と時刻は日本時間を基準とする。平日は月〜金とし、祝日は考慮しない（MVP の範囲外）。
- チャネルで直接 `まとめ` を呼んだ場合の対象は直近7日とする。
- ボットは自分の投稿を分析の対象から除く。
- AI には、会話の本文と参加者の表示名を送る。送る範囲はボットが招待されたチャネルだけで、AI の提供元は入力を学習に使わない契約のものを使う。
- 分析の結果（まとめ、ToDo）は、最後の更新から90日で削除する。
- 評価データは合成した会話だけで作り、実際の会話は使わない。
- 実行環境（受付と処理のサービス、キュー、定期実行、データの保存、秘密情報の管理）は作成済みで、それを使う。
- 範囲外: Slack 外のカレンダーとの連携、祝日の考慮、ToDo の手動での編集（ボットへの文での追加・変更）、複数ワークスペース、英語での出力。
