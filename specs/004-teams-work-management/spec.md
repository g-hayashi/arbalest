# Feature Specification: Teams の ToDo と共有記録

**Feature ID**: `004-teams-work-management`
**Feature Branch**: `main`（feature の保存先とブランチ名は独立）
**Created**: 2026-10-26
**Status**: ローカル実装・フェイク接続テストあり。実サービスの導入確認は未完了
**Input**: [既存設計](../../docs/teams-work-management-design.md)の正式化。標準チャネルの元スレッドで ToDo を登録・完了・通知し、更新可能な共有記録を残す。

## User Scenarios & Testing

### User Story 1 - ToDo を登録して安全に完了する (Priority: P1)

参加者はまとめから条件を満たす ToDo を登録し、候補と登録済み項目を一覧で確認する。担当者または最初の登録者がカードか明示コマンドで完了する。再分析しても同じ作業の状態を維持する。

**Why this priority**: 記録と通知の前提になる作業状態を、会話の再分析から独立して維持するため。
**Independent Test**: 合成会話で登録、候補選択、再分析、完了、無権限操作を行い、番号・担当者・期限・状態を照合する。共有記録と通知を無効にして検証できる。

**Acceptance Scenarios**:

1. **Given** 根拠一致・明示的・要確認でない未完了作業と参加者に存在する担当者がある、**When** `@arbalest まとめて`、**Then** 期限未定でも1件登録し、スレッド内番号を表示する。
2. **Given** 担当未定または曖昧な候補、**When** `@arbalest todo` と候補の「登録」、**Then** 根拠を確認して明示登録でき、担当未定は「登録者が管理」と表示する。根拠不一致は登録しない。
3. **Given** 登録済み項目、**When** 抽出順序が変わる・完了項目が再抽出される、**Then** 同じ作業の番号と状態を維持する。根拠が重なる曖昧な候補は関連付けか別件登録を求める。
4. **Given** 担当者または登録者、**When** 「完了」か `@arbalest done T12` を同時に複数回操作する、**Then** 変更は1回だけで、以後は完了済みとして応答する。他スレッドの番号・転送カード・無権限操作では変更しない。
5. **Given** 既存 ToDo と異なる担当者・期限の再抽出、**When** 更新候補を表示する、**Then** 担当者または登録者が確認するまで元の値を維持する。自然文の「終わった」や抽出上の完了だけでは台帳を完了しない。
6. **Given** 登録済み項目、**When** 根拠が編集・削除される、候補が消える、履歴を取得できない、**Then** 自動削除・完了せず既存状態を維持する。

### User Story 2 - まとめを更新可能な記録として読む (Priority: P2)

参加者は元スレッドの管理投稿で、概要・決定・未決定・ToDo・問い・根拠・更新日時を確認する。返信だけの依頼も選べる。

**Why this priority**: 同じ内容を探し直さず、最新の作業状態と根拠を参照できるため。
**Independent Test**: 共有記録の作成・更新・分割・完了反映・作成結果不明の復旧を合成会話と送信の代替実装で確認する。外部記録と通知は不要。

**Acceptance Scenarios**:

1. **Given** 検証済みの調整事項がある会話、**When** まとめを依頼する、**Then** 管理投稿を作成または更新する。概要しかない会話は返信だけとする。
2. **Given** 任意の会話、**When** `@arbalest canvas`、**Then** 調整事項の有無にかかわらず記録できるが、ToDo は新規登録しない。
3. **Given** 返信だけの依頼、**When** `@arbalest 返信だけでまとめて`、**Then** ToDo 登録と共有記録の更新を行わない。`todo` だけでは外部記録を新規作成せず、`findings 7` は振り返り返信だけとする。
4. **Given** 大きな記録と既存管理投稿、**When** 記録が分割・縮小される、**Then** 安定した順序で表示し、余った投稿は統合済みと示す。省略を完全な記録とは表示しない。
5. **Given** 台帳の完了保存が成功し記録更新が失敗した、**When** 再試行する、**Then** 完了を維持して表示だけを更新する。新規投稿の成否不明時は自動作り直しを止め、管理者の再関連付けか明示再作成を求める。
6. **Given** 削除済みの管理投稿、**When** 通常の自動更新、**Then** 勝手に再作成せず、明示的な再取得・canvas 操作でのみ再作成する。

### User Story 3 - 元スレッドで期限通知を受け取る (Priority: P2)

参加者は営業日09:00 JSTに元スレッドで未完了作業の集約通知を読み、最初の管理操作の依頼者が通知停止・再開を選ぶ。

**Why this priority**: 個人宛の追加導入を伴わず、作業の期限と完了方法を共有するため。
**Independent Test**: 金曜・月曜の時刻を固定し、期限、通知停止、同日再実行、完了競合、分割再開を検証する。外部記録を使わず検証できる。

**Acceptance Scenarios**:

1. **Given** 管理対象の通知有効スレッド、**When** 月〜金09:00 JST、**Then** 次の営業日までが期限の未完了項目（期限超過を含む）を1日1組で通知し、期限未定は月曜だけ含める。金曜は月曜までが対象となる。
2. **Given** 通知対象、**When** 通知する、**Then** 表示名・受信理由・期限・根拠リンク・完了方法・停止方法を示し、個人メンションや DM を使わない。
3. **Given** 最初の管理操作の依頼者、**When** `@arbalest 通知停止` または `通知再開`、**Then** 元スレッドだけを変更する。他の参加者は変更できない。
4. **Given** 同日の通知予約または送信済み部分、**When** 同時実行・再試行・同日の作業追加、**Then** 別の通知組を作らず、送信済み部分を再送せず、追加分は翌営業日へ回す。送信直前に完了・停止・期限切れなら除外する。

### User Story 4 - 任意の外部一覧へ共有記録を同期する (Priority: P3)

管理者が準備し閲覧範囲を確認した SharePoint List にスレッドごとの記録を同期し、参加者が元スレッド・根拠・人のメモを参照する。

**Why this priority**: Teams 内の記録を先に提供でき、外部同期は権限と共有範囲を確認して追加できるため。
**Independent Test**: 専用の外部記録代替実装で重複作成防止、競合、応答紛失、人のメモ保持、超過時停止を検証する。実接続の有効化判定は利用者が別途行う。

**Acceptance Scenarios**:

1. **Given** 専用 List とチャネルの対応および共有範囲の確認済み、**When** 同期する、**Then** 1スレッド1行で生成内容と人のメモを分け、元スレッドと根拠を開ける。
2. **Given** 作成・更新の成功後に応答を失う、**When** 復旧する、**Then** 同じ行と送信予定の内容を照合して二重作成・誤競合を防ぐ。
3. **Given** 人がメモだけを変更した、**When** 次の同期、**Then** メモを保持して生成内容だけを更新する。人が生成内容を変更した場合は競合として停止し、明示的な修復を求める。
4. **Given** 生成列が8,000文字を超える、**When** 同期する、**Then** 既存内容を維持して超過を知らせる。切捨てや別文書への自動転記は行わない。
5. **Given** 権限または共有範囲が未確認、**When** 外部同期を有効化しようとする、**Then** 有効化を保留する。誤共有発覚時は同期を止め、保存済み内容の共有範囲・削除を管理者が処理する。

### Edge Cases

- 同じ生メッセージ ID、同時刻、親と返信、別スレッドの根拠を混同しない。作業本文の否定語・数字・日付を保持して照合する。
- 古い・改変済み・転送済みカード、異なる組織や会話、担当者変更後の操作を拒否し、最新一覧の取得を案内する。拒否により ToDo 内容や人物情報をチャネルへ追加公開しない。
- 送信成功後の保存失敗では通知重複が残り得る。送信と同時の完了では直前状態の通知が届き得る。厳密な一度だけの送信は保証しない。
- 新旧の更新が競合した場合は最新内容を再適用する。履歴不足、外部同期失敗、表示失敗を台帳の失敗と混同しない。
- 保持期限の境界では削除待ちでも操作・通知を拒否する。期限切れの根拠から自動再登録しない。

## Requirements

### Functional Requirements

- **FR-001**: 標準チャネルの元スレッド単位で ToDo を管理し、Slack の検索・一覧・通知と分離する。個人・グループチャット、private/shared channel は対象外とする。
- **FR-002**: 全登録候補に実在する元メッセージと一致する引用を必要とする。不一致・不完全な履歴では登録と外部更新を止め、既存台帳を維持する。
- **FR-003**: 自動登録は根拠一致、取得会話に存在する担当者、要確認でない、明示的、未完了の全条件を満たすものに限定する。期限未定を許す。候補の明示登録は担当未定を許し、根拠検証は省略しない。
- **FR-004**: 永続的な作業の識別子とスレッド内で単調増加する表示番号を分け、抽出順序の変更でも同一作業を維持する。同じ元メッセージ・引用・作業本文が双方1件だけ一致するときだけ自動対応させる。
- **FR-005**: 本文・根拠の変化や複数一致は自動統合せず、関連付けか別件登録を求める。担当者・期限の差は担当者または登録者の確認まで反映しない。消失・削除・再抽出から既存の完了・削除・再開を推測しない。
- **FR-006**: 完了は担当者または最初の登録者だけに許し、同時操作でも変更は1回とする。完了済みへの再操作は成功済みと返す。取消・再開・任意の担当者手動変更は初版に含めない。
- **FR-007**: カードと明示コマンドの操作者・会話・対象・有効期限・最新状態を認証済み情報で検査する。カードは発行7日または台帳保持期限の早い方までとし、古い状態を適用しない。操作受付と実行の両方で再検査する。
- **FR-008**: `まとめて`、`返信だけでまとめて`、`todo`、候補の登録・関連付け・更新確認、`done T番号`、`canvas`、`通知停止`、`通知再開`、`findings 日数` を各ストーリーの動作で提供する。依頼の ToDo 抑止・記録抑止を別々に尊重し、抑止した副作用から別の新規副作用を有効化しない。
- **FR-009**: 自動記録は検証済みの調整事項（話題、未完了 ToDo、未解決の問い）がある場合だけとし、明示 canvas は条件外でも許す。記録に最新台帳の状態を重ね、完了時は既存記録へ反映する。
- **FR-010**: 管理投稿はボット所有の元スレッド内投稿だけを更新する。分割と縮小を追跡し、削除済み投稿は明示取得時だけ再作成する。新規作成結果不明では自動再作成を停止し、管理者の確認と再関連付けか明示再作成を必要とする。
- **FR-011**: リマインドは月〜金09:00 JST、次営業日までが期限の未完了が対象、期限未定は月曜のみとする。祝日除外は行わない。元スレッドで1日1組、個人メンションなしとし、通知停止・再開は最初の管理操作の依頼者に限定する。
- **FR-012**: 同日の追加・変更から別通知組を作らず翌営業日へ回す。送信済み部分を再送せず、送信直前に完了・停止・期限切れを再検査する。宛先を変更しての自動迂回を行わない。
- **FR-013**: 認証・権限エラーでは通知を停止して再接続を案内し、対象消失では無効化する。頻度制限に従って待ち、一時障害は上限付き再試行後に失敗状態を保持する。キュー投入失敗を受付成功と返さない。
- **FR-014**: 任意の外部記録は管理者が準備した専用 SharePoint List だけとし、標準チャネルと同じ閲覧範囲を確認してから有効化する。サイト探索、任意保存先、List・タブ自動作成をしない。
- **FR-015**: 外部記録は1スレッド1行を基本とし、一意なスレッドキー、概要・決定・未決定・ToDo・問い・根拠・日時・版と人のメモを分離する。生成列はプレーンテキストで各8,000文字以下とし、超過は既存行を維持して停止する。
- **FR-016**: 作成・更新の応答紛失時は行の識別子と送信予定・適用済み内容を照合して復旧する。人のメモは保持し、生成列の人の編集は自動上書きしない。競合時はスレッドに修復が必要と示す。
- **FR-017**: 分析・登録・管理投稿・外部同期・結果返信を別の進捗として保持する。再試行は確定済みの表示を再利用し、分析を繰り返さない。古い更新は停止し、表示の順序逆転は最新内容の定期修復で回復する。
- **FR-018**: 登録・人による更新・完了から90日を保持期間とし、自動分析・通知・表示更新では延長しない。期限切れ操作を即時拒否し、90日超の根拠から自動再登録しない。外部投稿・行は各サービスの保持方針に従い、自動削除を保証しない。
- **FR-019**: 新機能は既定無効とし、無効化・アプリ削除で送信と新規登録を停止する。保存済み記録の自動削除は行わない。外部同期は最小権限と専用 List 外の拒否を利用者が確認するまで有効化せず、失敗時に権限を自動拡大しない。

### Key Entities

- **ToDo**: 永続識別子、スレッド内番号、本文、担当者、登録者、期限、未完了/完了、版、根拠、保持期限。
- **照合候補**: 元メッセージ・引用・本文と既存 ToDo の対応。曖昧・更新待ち・新規・既存を区別する。
- **管理対象スレッド**: 組織・チーム・チャネル・親投稿、最初の管理者、通知状態、認証済み返信先。
- **操作参照**: 操作対象、許可操作、対象版、元カード、有効期限。利用者入力のみから対象を決めない。
- **共有記録と通知**: 確定した表示内容、版、投稿・行、送信部分、適用状況、失敗と復旧状態。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 合成会話の順序変更・同時登録・再分析・完了再抽出の各シナリオで、誤った作業への状態継承と重複登録が0件、同時完了の状態変更が1回となる。
- **SC-002**: 異なる組織・スレッド、無権限、転送・改変・期限切れの操作を全件拒否し、台帳変更と拒否通知による内容の追加公開が0件となる。
- **SC-003**: 金曜・月曜・期限未定・停止・完了・同日再試行の全シナリオで、通知対象と日次予約が要件に一致し、成功を記録済みの通知部分の再送が0件となる。
- **SC-004**: 台帳成功後の表示失敗・外部失敗・応答紛失から、保存済みの状態を失わず失敗箇所だけ復旧でき、人のメモの消失と生成列の無断上書きが0件となる。
- **SC-005**: 返信だけ、概要だけ、明示 canvas、todo、findings、各抑止のシナリオで副作用が全件要求どおりとなり、既存 Slack の作業検索・通知へ混入する Teams 項目が0件となる。
- **SC-006**: 保持90日の境界および外部生成列8,000文字の境界で、期限切れ操作・通知と超過内容の自動切捨てが0件となる。

## Assumptions

- 003 の標準チャネル取得・分析・認証・キュー・返信を再利用する。003 T014 の実接続確認は未完了の独立した利用者タスクであり、004 で完了とみなさない。
- 合成データと代替実装による TDD を行う。実 Teams・SharePoint・AI・Firestore の検証は利用者が行い、本番 GCP とインフラは変更しない。
- Teams への導入と認証済み会話参照が能動通知の前提。外部 List の準備、最小権限、閲覧範囲、desktop/web/mobile の確認は導入時の有効化条件とする。
- リアクションによる合意・完了、Planner、Microsoft To Do、DM、Loop、独自タブ、SharePoint ページ自動生成は対象外。Teams 内記録は共同編集 canvas の再現ではない。
- カードのクライアント対応と外部 List の最小権限は実環境確認を残すが、機能を仕様から削除する理由とはしない。詳細な通信・保存・復旧方式は計画と契約に定める。
